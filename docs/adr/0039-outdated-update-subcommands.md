# `lwpt outdated` and `lwpt update` are the Dependabot-equivalent for the LWPT ecosystem

The subcommand surface, frozen at twelve since [ADR-0027](./0027-agents-subcommand.md) and the pre-approved [ADR-0006](./0006-stack-contracts-deferred-from-v1.md) pair (`health`, `duplication`) ([Hard Constraint in AGENTS.md](../../AGENTS.md)), expands to fourteen with `lwpt outdated` and `lwpt update`. The problem they solve: every LWPT consumer (wasmlight, duetto, lakon, and any later git-host dep) has no sanctioned way to learn that a newer tag exists, rewrite the authored `^`/`~` constraint when the latest release is outside it, and land a lockfile that still went through the install transaction. Today the documented path is `lwpt add <source@new-version>` or a hand-edit plus `lwpt install`. That is fine for one package, one human; it is not a weekly ecosystem loop. Dependabot cannot read `lwpt.toml`. We chose two thin frontends over the existing resolver and git smart-HTTP tag listing ([ADR-0009](./0009-source-syntax-and-tag-resolution.md)) rather than a new HTTP/JSON GitHub-releases client because the tag advertisement is already host-uniform, already fixtureable (`LWPT_TEST_GIT_FIXTURE_DIR`), and already what `lwpt install` trusts. Release notes stay out of the binary.

## Subcommand contracts

- **`lwpt outdated [--json]`** — load the current project's `lwpt.toml` and `lwpt.lock`. For each direct git-host dependency (`owner/repo`, `github:`, `gitlab:`, `bitbucket:`, or a `[sources.<name>]` custom host), list remote refs via the existing smart-HTTP path and take the highest SemVer tag. Compare that latest tag to the authored constraint and the lockfile's `resolvedRef`. Print `name`, `constraint`, `locked`, `latest`, and `status` (`current` / `newer` / `major`). Exit 0 when every compared dep is `current`; exit 1 when any is `newer` or `major`. A 0.x minor bump is `major` (SemVer 2.0.0 pre-1.0 breaking change). Workspace packages (`workspace:auto` / `skWorkspace`), local paths, and URL tarballs are skipped — they have no remote tag list that LWPT owns. Missing lockfile: locked column is empty and any advertised newer tag is `newer`/`major`. No advertised SemVer tag: the dep is omitted (nothing to compare).
- **`lwpt update [name ...]`** — if names are given, only those; otherwise every dep `outdated` would flag as `newer` or `major`. Unknown, workspace, local, or URL names are hard errors. When the latest tag is already inside the authored constraint, the constraint is left alone and the existing install transaction refreshes `lwpt.lock` / `lwpt.cfg`. When the latest tag is outside the constraint, the constraint is rewritten in place while preserving the authored operator: `^1.2.3` + `2.0.0` becomes `^2.0.0`; `~1.2.3` + `1.3.0` becomes `~1.3.0`; an exact `1.2.3` becomes `1.2.4`. Other range spellings that cannot keep a leading `^`/`~` become `^<latest>`. SHA and literal-tag pins become the published latest tag. The edit is comment-preserving and handles both the bare `name = "source@spec"` form and a single-line inline table's `version = "..."` key (so `include`/`exclude` globs survive). The lockfile is never hand-edited: the mutation or install transaction is the only writer, same as [ADR-0019](./0019-add-remove-subcommands.md).
- **Network posture:** both commands list remote refs. `update` may also fetch archives through the install transaction. They join `install` / `add` / `remove` on the "network operations are explicit" boundary.

## Considered Options

- **Keep the surface at twelve; document `lwpt add` / hand-edit.** Smallest change; no ADR. Rejected because the weekly ecosystem loop has no owner: Dependabot cannot parse `lwpt.toml`, and asking every consumer to invent their own cron is how lockfiles rot.
- **A new GitHub Releases HTTP/JSON client.** Would give release notes inside the binary. Rejected: tag listing already exists, is host-uniform, and is what the resolver trusts. Notes belong with whoever opens the bump PR, not in the CLI.
- **`lwpt install --update` instead of a new verb.** No surface expansion. Rejected for the same reason ADR-0019 rejected `lwpt install <pkg>`: `install` means "materialize the manifest", and overloading it to mutate constraints muddies `--frozen`.
- **Dependabot-native metadata / a registry.** The self-hosted registry is still [issue #29](https://github.com/frostney/lwpt/issues/29). This ADR ships the git-host path that every current consumer already uses.

## Consequences

- The frozen-surface Hard Constraint's canonical set becomes `init`, `install`, `add`, `remove`, `outdated`, `update`, `build`, `format`, `duplication`, `test`, `repair`, `run`, `health`, `agents`. `outdated` and `update` join reserved run-task names so an `[outdated]` / `[update]` section is a manifest-load error.
- `LWPT.DependencyUpdate` owns comparison, skip rules, constraint bumping, and report rendering, with co-located unit tests that inject ref lists (no network in CI). `LWPT.ManifestEdit` gains a version-only line edit so inline tables keep their globs.
- Weekly automation (a reusable GitHub Action that runs these commands and opens a PR) is out of this change. It lands in a follow-up PR.
- The decision **forecloses** a later GitHub-releases client inside the binary and **opens** a future "outdated --transitive" view if lockfile-only bumps ever need a separate report.
