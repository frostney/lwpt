# Commit-SHA pins must be reachable from an advertised branch or tag

Issue [#303](https://github.com/frostney/lwpt/issues/303) found that a dependency pinned to a commit SHA installed whatever the host's archive endpoint served for that id. GitHub and GitLab serve commits that exist only in forks, pull requests, or merge requests under the upstream repository's name, so `actions/checkout@c7d749a2d57b4b375d1ebcd17cfbfb60c676f18e` (Chainguard's documented imposter commit) installed fork code that looks like upstream. When every requirement for a dependency was a SHA, resolution skipped ref listing entirely.

This ADR amends [ADR-0009](./0009-source-syntax-and-tag-resolution.md) and the AGENTS.md hard constraint "Git sources use HTTP archive endpoints, not the git protocol". Archives remain the only source of dependency content. The git smart-HTTP upload-pack service, already used for tag listing, may now also carry commits-only reachability proofs.

## Threat model

The proof answers one question: is this commit id part of the upstream repository's own branch or tag history? It defends against an honest host that serves fork-only objects under the upstream name, and against a manifest, pull request, or copied snippet that pins such an object.

It does not defend against a compromised or malicious host. That host is already trusted to advertise the upstream refs and to serve archive contents. It could advertise a forged branch, or answer the archive request for a proven commit with other content, including after the proof finished. LWPT does not bind archive bytes to the commit's tree: that would need trees and blobs over the git protocol, which this ADR keeps out of scope. After the first install, the lockfile's `archiveHash` and `computedHash` bind the content, and `--frozen` verifies them. What the proof does ensure is that host-supplied evidence it cannot verify is never accepted. Peel claims never count as proof; framing without an answer, contradictory or unsolicited acknowledgments, malformed ref names, malformed tag objects, over-limit listings and packs, and responses that exceed the proof's byte or time budget (redirect bodies and local parsing included) fail the proof.

## Decision

- **A commit-SHA pin is accepted only when the commit is reachable from an advertised `refs/heads/*` or `refs/tags/*` tip.** `refs/pull/*`, `refs/merge-requests/*`, and every other namespace never count. The rule applies to every SHA requirement: alone, or beside a tag, range, or branch requirement from another manifest. In the mixed case the resolver selects the commit through the named ref, possibly via the listing's unverified peel line, so the SHA is proven exactly like a lone pin and its proof is recorded the same way.
- **Every commit requirement must be a full 40-character SHA**, whether it stands alone or next to a named requirement from another manifest. An abbreviated pin fails online resolution with an error that names the requirer and asks for the full SHA. A prefix cannot be proven: some hosts resolve it to any matching object, including one that exists only in a fork.
- **Exact tip first.** If the pin equals the object a well-named branch or tag points to in the listing the resolver already makes (`info/refs`), it is accepted with no extra request. A peel line (`^{}`) is the host's claim about an annotated tag's target, not evidence, so a pin that only matches a peel goes through the proof below. There, the tag object itself arrives hash-verified in a pack.
- **Otherwise, a set-difference proof over protocol v2** (`LWPT.GitProtocol.ProveCommitReachable`):
  1. `GET <repo>/info/refs?service=git-upload-pack` with `Git-Protocol: version=2`. The host must offer `ls-refs` and `fetch` with the `filter` feature, and a `sha1` object format. Otherwise the pin is refused and the error suggests pinning a tag or branch.
  2. `ls-refs` with `symrefs` and prefixes `HEAD`, `refs/heads/`, `refs/tags/` gives the tips as the objects the refs name (an annotated tag's own object id) and the default branch. `peeled:` attributes are ignored. Ref names must pass git's check-ref-format rules (at least one slash; no control characters, spaces, `~^:?*[\`, `..`, empty or dot-led components, `.lock` components, and so on); a listing with an invalid branch or tag name is refused. The resolver's legacy `info/refs` listing is parsed with the same name rules, strict pkt-line framing (including the terminating flush, distinct from a service preamble's), its own count limits, and an indexed (linear) peel lookup. The proof-only `MAX_PROOF_TIPS` cap does not apply to it, so named requirements work in repositories of any size up to those limits.
  3. One shallow `fetch` (`deepen 1`, `filter tree:0`) of the tips and the pin gives their committer dates. A tag tip's date is its verified target commit's. The dates only order the next step. A host that declines this request (an `ERR` line or side-band error) leaves the probes unordered; anything it does send is evidence, so an invalid or over-limit pack, a budget breach, or a transport failure fails the proof.
  4. Up to four tips committed closest after the pin, then the default branch, are probed one at a time with `want <tip>`, `have <pin>`, `filter tree:0`, and no `done`. A tip that cannot reach the pin costs only an acknowledgment. When the host is ready, it streams `pack(tip --not pin)`. An explicit `NAK` means the host has no such object, so the pin fails as unknown. An answer with neither `ACK`, `ready`, nor `NAK`, a malformed `ACK`, an `ACK` for an object that was not offered, `NAK` beside `ACK` or `ready`, or any acknowledgments in answer to a request that sent `done` is a protocol error, not a verdict; every fetch answer is checked against its own request.
  5. The remaining tips go in one final round, with `have` for the pin and for every probed tip whose pack proved it does not contain the pin.
  6. Every pack is requested with `filter tree:0` and without `thin-pack`. `LWPT.GitPack` recomputes each commit's and annotated tag's SHA-1 from the received bytes and walks from the tips through tag targets and parent links. The pin is reachable if and only if a received commit lists it as a parent or a received tag names it. The walk is complete: every object on a path from a tip to the pin is not an ancestor of the pin, nor of an excluded tip (that tip would then contain the pin), so the host must send it. The walk is sound: every hop is hash-verified from an advertised tip.
- **Negotiation alone is never trusted.** upload-pack marks a `have`'s parents as common, so `ready` also fires for a fork commit that sits on top of upstream history.
- **Limits** (named constants, all fail closed):
  - `MAX_UPLOAD_PACK_RESPONSE_BYTES` (64 MiB) per response, enforced while reading through `HTTPClient`'s `MaxResponseBodyBytes`. An oversized response raises the new `EHTTPResponseTooLarge` (`httpclient` 0.5.0, the same unreleased bump as ADR-0048) and the pin is refused.
  - One budget for the whole proof: `MAX_REACHABILITY_PROOF_MILLISECONDS` (180 s) on a monotonic clock and `MAX_REACHABILITY_PROOF_BYTES` (128 MiB). Each request may use only what is left, so a slow host cannot stretch a proof to the sum of per-request timeouts. The capability request follows redirects itself, one hop at a time, so every redirect body is charged to the same budget. The deadline also bounds pack parsing, delta resolution, and the graph walk, and is checked again before every verdict, including an exact match in the `ls-refs` listing.
  - Listings: `MAX_ADVERTISED_REFS` (100,000 branches and tags, or ls-refs lines) and `MAX_REF_NAME_LENGTH` (1,024 bytes) everywhere; a legacy advertisement is also capped at `MAX_LEGACY_ADVERTISEMENT_LINES` (1,000,000) because it carries refs that are dropped. The proof's `ls-refs` listing is further capped at `MAX_PROOF_TIPS` (20,000 distinct tips, deduplicated in linear time) because every tip can become a `want`; past it the proof fails with an error that says to pin a tag or branch. Requests, closing flush included, are capped at `MAX_UPLOAD_PACK_REQUEST_BYTES` (2 MiB).
  - The pack reader caps the object count (`MAX_PACK_OBJECT_COUNT`, 1,000,000), each inflated object and delta result (`MAX_PACK_OBJECT_BYTES`, 8 MiB), the total inflated bytes (`MAX_PACK_INFLATED_BYTES`, 256 MiB), and the inflate ratio (`MAX_PACK_INFLATE_RATIO`, 32 times the pack size plus 1 MiB).
  - It range-checks every delta instruction, resolves `REF_DELTA` bases that appear before or after the delta, and rejects trees, blobs, thin packs, delta cycles, checksum mismatches, tag objects without the `object`, `type` (commit, tree, blob, or tag), and `tag` headers git requires, and trailing bytes.
  - A proof makes at most nine logical requests after the listing (redirect hops of the capability request are extra HTTP requests inside the same budget).
- **Scope of the git protocol.** Only ref listing and commits-only reachability proofs. No tree or blob is requested or accepted. Content still comes from the archive endpoint and is hashed into the lockfile as before. LWPT speaks HTTP only and never runs `git`. Every upload-pack request carries the dependency's destination policy (`LWPT.FetchPolicy`, [ADR-0048](./0048-git-host-fetch-trust.md)), like ref listing and archive fetches. Commands are posted to the repository URL that the capability request resolved, so a renamed repository keeps working.
- **Proof provenance in the lock.** A proven SHA pin's lock entry records the proving ref as `reachableFrom = "refs/tags/v1.2.0"`, an additive schema-v3 field like `resolvedRefKind`, for lone and mixed SHA requirements alike. Only a valid full ref under `refs/heads/` or `refs/tags/` counts; an entry without it, or with any other value (written before this ADR, or by hand), carries no evidence.
- **When the proof runs.** Whenever an online install, `add`, `remove`, or `update` selects a dependency with a SHA requirement, unless the lock entry has the same source identity, the same commit, and a valid `reachableFrom`. Such an entry was proven when written and is trusted like the committed archive it names. A new entry, a changed commit, or an entry without valid provenance is proven before it is published. If the ref listing fails, a locked entry is reused only when it records valid provenance.
- **Frozen and offline installs stay network-free.** They install an entry with a SHA requirement but without valid `reachableFrom` from its verified hashes, and print a warning naming the dependency and commit that tells the user to run `lwpt install` online. Failing them would break every existing CI lock at once without adding protection: the marker is machine-written but, like the rest of the lock, is not a signature.
- **The lockfile schema version does not change** (v3; `reachableFrom` is additive and optional).

## Considered Options

- **Negotiation only (`ready` without a pack).** Cheapest. Rejected as unsound: the linux `refs/pull/932/head` commit and the actions/checkout imposter both got `ready` or `ACK` from a branch that does not contain them.
- **A `deepen-since` graph walk.** Rejected: skewed commit dates reject valid pins, and it transfers more than the set difference (vscode: 97.9 MB against 16.5 MB).
- **Host APIs such as GitHub's compare endpoint.** Rejected for the reasons in ADR-0009: host-specific, JSON, and rate-limited.
- **Trust `^{}` peel lines for exact-tip matches.** Rejected: a peel is an unverified claim. Wanting the tag object costs one probe and yields the same answer from hashed bytes.
- **Bind archives to the proven commit's tree.** Out of scope here. It needs trees and blobs over the git protocol, and `export-ignore`, `export-subst`, and submodules make archive contents legitimately differ from the tree. See the threat model.
- **Re-verify every locked pin on every online install.** Rejected. It adds requests to every install and fails installs that were already reviewed once upstream rewrites history. Proving a pin when it enters or changes the lock, or when its entry has no recorded proof, catches the attack (a manifest or PR that pins fork code), while the lock itself is reviewed like any committed content.
- **Fail `--frozen` and `--offline` on entries without `reachableFrom`.** Rejected: see the decision above; the warning keeps them network-free and explicit.
- **Accept abbreviated SHAs with a warning.** Rejected: an unverified pin is the defect this ADR removes.

## Consequences

- A lone pin to a fork-only, pull-request-only, or unknown commit fails before its archive is fetched, and nothing is published. When the SHA arrives beside a named requirement in a later resolver round, a candidate archive for the named ref may already have been staged, but nothing is published. `lwpt add` leaves `lwpt.toml` unchanged (ADR-0019's install-before-write ordering).
- Existing locks gain `reachableFrom` on their next online install, which proves each unmarked SHA pin once. Until then, `--frozen` and `--offline` warn about them.
- Abbreviated SHA pins that installed before now fail online resolution, including a transitive abbreviated pin next to a named requirement. `--frozen` and `--offline` keep working from an existing lock. The README example uses a full SHA.
- A pin can become unprovable. If upstream force-pushes or deletes the only branch that contained the commit, the next proof of that entry fails with an error naming the commit. Entries that record their proof keep installing. Users see this as "pin a commit from the repository's own history".
- Hosts without protocol v2 `filter` support can still use pins that equal an advertised branch or lightweight tag. Other pins on those hosts must switch to a tag or branch. GitHub, GitLab, Bitbucket, and Codeberg all advertise `filter`.
- Commit pins in repositories with more than 20,000 distinct branch and tag tips cannot be proven unless they equal a listed tip; such pins must switch to a tag or branch. Named requirements are unaffected up to the listing's own 100,000-ref limit.
- Cost, measured against live hosts (spike and `LWPT_ENABLE_NETWORK=1` tests):
  - Exact-tip pins cost nothing beyond the listing.
  - The actions/checkout imposter commit is refused after 9 requests and 260 KB.
  - A 2023 actions/checkout commit is proven through `v3.5.3` in 4 requests and 88 KB.
  - Nearest-tip probing keeps old pins in large repositories small. For a 2015 linux commit, the spike measured 506 KB through the nearest tag against 489 MB from the default branch.
  - Proofs that genuinely need more than the per-response or total budget, such as a fork commit based on old linux history, are refused rather than trusted.
- FPC's SHA-1 has no collision detection. Forging a path would need a second preimage of an existing commit, so the risk is accepted.
- Recorded upload-pack exchanges under `tests/fixtures/git-reachability/` are keyed by the SHA-256 of the request body. A change to the requests the prover sends must re-record them with the command in `source/LWPT.GitProtocol.Test.pas`.
